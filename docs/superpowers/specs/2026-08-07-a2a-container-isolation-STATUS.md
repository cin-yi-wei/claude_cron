## 為什麼暫停

派委派任務進來的**只有 operator 自己的 `cc-` binding**。

`cc-` binding 本來就以 operator 的身分在這台機器上執行，沒有任何限制。一個會惡意委派的 `cc-` session 不需要繞道 A2A —— 它直接做就好，連權限閘都不會經過。因此容器要防的那個攻擊者，在這個威脅模型下不存在。

成本則是實的：15 個 task、併發上限從 8 降到 4（可用記憶體 5.2 GiB）、外加尚未解決的容器內認證。

**這個判斷完全建立在「呼叫方只有自己人」上。** 一旦要開放外部 agent 連進來，結論反轉，本文與那兩份文件可以直接接續。

## 已經驗證過的東西（重要，不要重做）

在這台機器上實跑，不是推論：

**docker 可用、不需要 root。** Docker 29.1.3，operator 已在 `docker` 群組。這是容器方案相對「另開 unix 使用者」的主要優勢——後者需要一條 sudoers 規則。

**`--internal` 網路是封閉的。** 實測擋住 host 自己發佈的 `0.0.0.0:3306`（fatgame-mysql）、擋住 `docker0` 閘道、無對外出口。原規格把「是否需要一次性 root iptables 規則」列為開放問題，**此問題已結案：不需要**。

**容器看不到 operator 的憑證。** 容器內 `/home/conray` 不存在，`~/.claude/.credentials.json` 讀不到。這正是「另開 unix 使用者」方案（選項 2a）做不到、要 2b 再加一份獨立登入才有的性質。

**共用 repo 的 `.git` 全開可寫 = 容器逃逸。** 這是本次最重要的發現，原規格低估了它。

在容器內把 `pre-commit` 寫進共用 repo 的 `.git/hooks`，回到主機 commit，**主機執行了它**。程式碼因此從容器內跨到主機、以 operator 的身分執行。權限閘完全擋不到——那個 hook 不是沙盒觸發的，是之後某個 `cc-` session commit 時觸發的。`.git/config` 的 `core.pager` 同理。

原規格把這寫成「gate 的 git 規則因此不能刪」，實際嚴重度是「整個容器化失去意義」。

**上述逃逸有解，且已驗證。** 不要整個 `.git` 可寫，只開兩個子路徑：

- `<repo>/.git` 整體 `:ro`
- `<repo>/.git/objects` 可寫（commit 要寫物件）
- `<repo>/.git/worktrees/<name>` 可寫（index 在這裡）

實測結果：`git commit` 成功；寫 `.git/hooks` 被拒（Read-only file system）；寫 `.git/config` 被拒。

**共用 repo 模型因此保住**，不需要退回「每個沙盒各自 `git clone --local`」那個會改變交付模型的方案。原規格的第一號否決風險應從「必須接受」下修為「已解決」。

殘留：沙盒仍寫得到自己那個 worktree 的 gitdir，可以在裡面放 `config.worktree` 指向自己的 hooks 目錄。但那只影響它自己那個 worktree；實測主機在主 repo commit 不受影響。

## 尚未解決的一項

**容器內的 claude 如何認證。**

根本限制：容器裡的 claude 要能跑就必須拿到一份能用的憑證，而憑證能用，沙盒就能用它——它就是那個行程。不存在「用得了但偷不走」的憑證。可選的只有「給哪一份」與「出事多好撤」。

四個方向（詳見設計規格第六節）：掛 operator 的 `~/.claude`（放棄容器最大的好處）／環境變數餵 token（暴露程度相同）／另簽一份專供沙盒、可獨立撤銷的 token（當時的建議）／host 端認證代理（唯一真正拿不到，工程量最大，未驗證）。

**先決條件：另簽 token 的計費歸屬未確認**（會不會佔訂閱席次、或變成按量計費）。恢復這條路之前應先在後台確認，否則可能做完才發現每次委派都在燒錢。

## 恢復時的第一步

不要從 Task 1 重來。順序是：

1. 確認威脅模型是否仍為「只有自己人」。若已開放外部呼叫方，本方案的成本效益反轉，繼續。
2. 確認 token 計費歸屬（見上）。這一項不解決，Task 2 卡住。
3. 把上面「`.git` 只開兩個子路徑」的結論寫回設計規格第二節的掛載表，並下修第一號否決風險。計畫的 Task 2 應改為只驗認證（另外兩項已驗證完畢）。
4. 之後照 `111df64` 的順序走。Task 7（兩種隔離並存的開關）與 Task 10（孤兒容器回收）是最高風險：前者路由判斷錯會讓 sweep 對活著的容器執行 `tmux kill-session` 再刪掉它的掛載來源；後者是這輪唯一新增的破壞性路徑，必須走既有那條唯一的、有 `TryLock` 與身分重新確認的拆除路徑，不得自行另開。
